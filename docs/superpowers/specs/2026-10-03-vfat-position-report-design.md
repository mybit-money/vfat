# VFAT Position Report — дизайн

Дата: 2026-10-03  
Статус: утверждён пользователем

## 1. Цель

Создать переносимый персональный Codex-скилл и проектную инструкцию для построения дневного отчёта по доходу и автокомпаундам VFAT-позиций.

Первая версия должна:

- находить позиции произвольного кошелька через VFAT MCP;
- по умолчанию работать с кошельком `0x330d2a845d2df4e329034d72719c7c53f9c1f87a`;
- автоматически собирать NEST-позиции на HyperEVM;
- извлекать ончейн claims, автокомпаунды и расходы;
- строить агрегированную дневную таблицу в UTC;
- считать реализованный APR относительно капитала всех выбранных позиций;
- создавать JSON с полной детализацией и автономный интерактивный HTML-график;
- не требовать CSV и базы данных.

Архитектура должна позволить позже перенести расчётное ядро в TypeScript-проект `mybit-folio` и хранить нормализованные события в его БД.

## 2. Границы первой версии

### Входит в первую версию

- универсальное обнаружение позиций произвольного кошелька;
- ончейн-декодирование для HyperEVM/NEST;
- фильтры по сети, протоколу и reward-токену;
- агрегированный отчёт по всем выбранным позициям;
- детализация транзакций в JSON и по запросу пользователя;
- файловый кэш без БД;
- график совокупного капитала и APR.

### Не входит в первую версию

- автономный Python MCP-клиент;
- автоматическое скачивание CSV;
- график отдельной позиции;
- постоянная БД в Python-реализации;
- полная поддержка ончейн-декодирования всех сетей и протоколов.

## 3. Архитектура

Выбран гибридный вариант: Codex-скилл оркестрирует VFAT MCP, а переносимый Python-движок обрабатывает RPC, кэш, расчёты и визуализацию.

### 3.1. Поток данных

1. Скилл принимает кошелёк, период и фильтры.
2. Через VFAT MCP скилл получает позиции, их историю, капитал и доступную атрибуцию.
3. Ответы MCP преобразуются в версионированный нормализованный JSON.
4. Python-движок получает этот JSON, загружает и декодирует HyperEVM receipts через RPC.
5. Нормализованные транзакции и снимки капитала сохраняются в файловом кэше.
6. Расчётный слой формирует дневные агрегаты UTC.
7. Генерируются компактная таблица, полный `report.json` и автономный интерактивный HTML.

Python не обращается к VFAT через HTTP и не вызывает MCP самостоятельно. Все VFAT-данные проходят через `mcp__vfat__*` в соответствии с правилами проекта.

### 3.2. Значения по умолчанию

- Кошелёк: `0x330d2a845d2df4e329034d72719c7c53f9c1f87a`.
- Период: последние семь UTC-дней, включая текущие сутки.
- Сеть ончейн-декодирования: HyperEVM, chain ID `999`.
- Протокол/набор позиций: NEST.
- Reward-токены: сохраняются все найденные токены с возможностью фильтрации.
- Текущие сутки: включаются и помечаются предварительными.

## 4. Получение и выбор позиций

- Для VFAT discovery, истории и атрибуции используются только VFAT MCP-инструменты.
- Скилл запрашивает все доступные позиции кошелька, а не одну заранее выбранную позицию-получателя.
- Учитываются позиции, активные хотя бы часть выбранного периода, включая закрытые и мигрированные.
- Каждая позиция включается в капитал только на фактическом интервале своей жизни.
- Получатель компаунда определяется для каждой транзакции отдельно. Смена позиции-получателя внутри периода является штатным сценарием.
- Общий отчёт не зависит от конкретного получателя: claims суммируются по всем выбранным позициям-источникам.

## 5. Нормализованная модель транзакции

Минимальные поля:

- версия схемы;
- `chainId`;
- `transactionHash`;
- `blockNumber` и время UTC;
- административный кошелёк;
- Sickle-адрес;
- тип действия;
- признак автоматизации;
- `automationPaymentMethod`;
- позиции-источники;
- позиции-получатели;
- reward-токены, raw amounts, decimals и display amounts;
- токены и суммы, фактически добавленные в LP;
- USD-оценки и источник каждой оценки;
- показатели полноты;
- предупреждения и ошибки декодирования.

Транзакции дедуплицируются по `chainId + transactionHash`, отдельные движения — по `transactionHash + logIndex`.

## 6. Стоимость автоматизации

Для каждой транзакции рассчитываются:

- `grossClaim` — награда до удержаний;
- `automationFee` — фактически переданные VFAT токены;
- эффективный процент automation fee;
- `afterAutomationFee`;
- `netCompoundUsd` — стоимость реально добавленной LP;
- `executionLossUsd` — разница между стоимостью после automation fee и результатом исполнения;
- `networkGas` — `gasUsed * effectiveGasPrice`, нативная сумма, USD и адрес плательщика;
- `gasAccountDebit` — подтверждённое списание с gas account пользователя;
- `userAutomationCostUsd` — фактически понесённые пользователем расходы.

Ожидаемые 1,8% не должны быть захардкожены как фактическая сумма. Сумма определяется из ончейн-переводов, а отклонение от 1,8% порождает предупреждение.

Network gas keeper-а показывается справочно и не считается расходом пользователя без подтверждённого списания. Swap fee и price impact не выдаются за точно разделимые комиссии: их совокупный эффект отражается как `executionLossUsd`.

## 7. Капитал

- Основой служит почасовая история стоимости позиций из VFAT MCP.
- Дневной капитал считается средневзвешенным по времени.
- Последнее достоверное значение действует до следующей точки.
- Если достоверными данными покрыто менее 75% суток, капитал признаётся ненадёжным.
- Для ненадёжного капитала APR не рассчитывается.
- Неполные крайние дни не удаляются из таблицы.
- На графике ненадёжная точка заменяется разрывом.

## 8. Дневная агрегация и APR

Период режется строго по UTC. Новые дни выводятся сверху.

Для каждого дня сохраняются:

- дата и статус `complete`, `partial` или `unreliable`;
- средневзвешенный капитал USD;
- gross claims по токенам;
- gross claims USD;
- net compound USD;
- VFAT fee по токенам и USD;
- gas account debit и прочие подтверждённые расходы пользователя;
- число уникальных claim/compound-транзакций;
- число позиций-источников в детализации;
- реализованный net APR;
- покрытие данных о капитале;
- покрытие USD-оценок;
- предупреждения.

Основной счётчик клеймов — число уникальных транзакций. Batch-транзакция, собирающая несколько позиций, считается одной операцией; число источников хранится отдельно.

Для завершённых суток:

```text
economicNetUsd = netCompoundUsd - gasAccountDebitUsd
realizedAprPercent = economicNetUsd / averageCapitalUsd * 365 * 100
```

VFAT fee и потери исполнения повторно не вычитаются, поскольку уже отражены в `netCompoundUsd`.

Для текущих суток APR дополнительно делится на прошедшую долю UTC-дня и помечается предварительным.

Дни без операций включаются с нулевыми claims и APR `0%`, если капитал достоверен. При отсутствии надёжной USD-оценки токенные суммы сохраняются, а связанные USD-показатели и APR получают `null` с объяснением.

## 9. Файловый кэш

Кэш состоит из трёх уровней:

1. receipts и нормализованные транзакции;
2. снимки истории капитала;
3. производные дневные агрегаты.

Политика обновления:

- текущие сутки и два предыдущих завершённых дня обновляются всегда;
- более старые данные используются из кэша при совпадении версии схемы и алгоритма;
- `--refresh` принудительно пересобирает выбранный период;
- изменение версии расчёта инвалидирует производные агрегаты, но не исходные receipts;
- успешный receipt неизменяем и кэшируется без срока;
- отсутствующие и ошибочные RPC-ответы имеют короткий TTL.

В первой версии не используется база данных.

## 10. RPC

- RPC-запросы ограничиваются до 100 запросов в минуту.
- Поддерживаются повторы с увеличивающейся задержкой и резервный RPC.
- Для официального HyperEVM RPC учитывается ограничение `eth_getLogs` до 50 блоков.
- Предпочтительно использовать уже известные хэши из истории активности и получать receipts, не сканируя всю сеть без необходимости.
- Использованные RPC и проблемы доступности отражаются в диагностике.

## 11. Формат таблицы

Основная таблица:

| Дата UTC | Капитал, USD | Собрано gross, USD | APR net | Net compound, USD | VFAT fee, USD | Gas account, USD | Клеймов | Награды в токенах | Статус |
|---|---:|---:|---:|---:|---:|---:|---:|---|---|

Средние значения за весь период не рассчитываются и не выводятся.

## 12. Интерактивный HTML

HTML должен быть автономным и не зависеть от CDN или обязательной установки Plotly.

- X: UTC-дни.
- Левая ось: совокупный капитал USD.
- Правая ось: реализованный net APR.
- Серии можно включать и выключать.
- Tooltip показывает claims, net compound, VFAT fee, gas account, число операций и полноту данных.
- Ненадёжные точки образуют разрыв.
- Текущие сутки выделяются пунктиром и подписью «предварительно».
- Под графиком находится дневная таблица.
- Полная детализация остаётся в JSON и показывается по запросу.

## 13. Надёжность и диагностика

- Недоступные значения представлены как `null` с машинно-читаемой причиной, а не как ноль.
- Проверяется отсутствие двойного учёта транзакций, логов, automation fee и gas account debit.
- Проверяются токенные потоки до и после удержаний с учётом swap и остаточной пыли.
- Фактический VFAT fee сверяется с gross claim; отклонение от 1,8% даёт предупреждение.
- Повторный запуск на одинаковом входе должен формировать идентичные JSON и HTML.
- Диагностика сообщает покрытие капитала, долю USD-оценённых наград, использованные RPC и все предупреждения.

## 14. Тестовые сценарии

Fixtures должны покрывать:

- обычный fee-paid compound;
- compound через gas account;
- несколько позиций-источников в одной транзакции;
- смену позиции-получателя;
- одну транзакцию, встречающуюся в истории нескольких позиций;
- пропущенные часы капитала;
- покрытие капитала ниже 75%;
- неполные текущие сутки;
- отсутствующую USD-оценку;
- отличие фактического automation fee от 1,8%;
- keeper-paid network gas без пользовательского списания;
- инвалидацию производного кэша при смене версии расчёта.

## 16. Будущий перенос в mybit-folio

- Входной и выходной JSON-контракты должны быть технологически нейтральными.
- Python fixtures становятся golden fixtures для TypeScript-реализации.
- TypeScript-версия должна воспроизводить Python-результат на тех же fixtures.
- БД и долгосрочное хранение всех транзакций принадлежат `mybit-folio`, а не переносимому Python-скиллу.
- Перенос оформляется отдельным handoff после стабилизации Python-эталона.
